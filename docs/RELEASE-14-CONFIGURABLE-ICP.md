## A. Current-State Findings — where ICP is hardcoded today

Verified by direct grep + reading, not assumption. **Four distinct locations**, more than previously documented:

### A1. Lead Scoring — Company Fit bonus
`src/lib/agents/lead-scoring.ts:285-289`
```ts
// Logistics industry bonus
const industry = (inputs.company.industry ?? "").toLowerCase();
if (industry.includes("logistics") || industry.includes("transport") || industry.includes("supply chain") || industry.includes("freight")) {
  companyFitScore = Math.min(25, companyFitScore + 5);
}
```
Affects the deterministic 0–100 score that drives classification (hot/warm/cold), opportunity eligibility, and CRM sync gating. This is the highest-impact hardcode — it silently favors logistics-adjacent companies for every tenant, regardless of what that tenant actually sells.

### A2. Follow-Up Agent — the AI system prompt itself
`src/lib/agents/followup-agent.ts:312`
```ts
const AI_FOLLOWUP_SYSTEM_PROMPT = `You are a RevOps consultant writing follow-up outreach for a
logistics/supply-chain sales team after a trade show conversation. ...
Prefer specific callbacks: "Based on our discussion regarding warehouse visibility challenges..."`;
```
The AI's persona and example callback are hardcoded to logistics *inside the prompt text*, not just in scoring logic. Every follow-up draft, for every tenant, is generated by an AI that believes it's writing for a logistics company. This is the clearest instance of the brief's warning against "solving configurable ICP by creating increasingly complicated prompts" — right now it's the opposite problem: one industry's assumptions are baked into the only prompt that exists.

### A3. Company Intel Tab — a second, independent "ICP fit" calculation
`src/components/lead-detail/CompanyIntelTab.tsx:59-77` — **new finding, not in the prior session's assessment.**
```ts
function deriveICPFit(company, score) {
  const logisticsKeywords = ["logistics", "freight", "transport", "supply chain", "shipping", "warehous"];
  const industryFit = !company?.industry ? "Unknown"
    : logisticsKeywords.some(k => industry.includes(k)) ? "Strong" : "Moderate";
  // ...size/revenue/strategic fit via separate hardcoded thresholds
}
```
This function backs a UI card **already labeled "ICP Match"** (Industry Fit / Company Size Fit / Revenue Potential / Strategic Fit), shown on every lead's Company Intel tab. Critically: **this is a second, disconnected fit calculation** — it does not read from `lead-scoring.ts`'s actual score breakdown, has its own arbitrary thresholds (employee count ≥200, opportunity value ≥$20k, companyFitScore ≥18), and its own separate logistics keyword list. Right now there are **two sources of truth for "fit"** in this codebase, not one — a direct violation-in-waiting of the brief's Engineering Principle ("There must be one source of truth for ICP configuration"). This needs to be resolved as part of R14, not just extended.

### A4. Cosmetic placeholder text (low priority, UX only — not a functional hardcode)
`src/app/capture/[tenant]/[event]/page.tsx:95,97`, `src/app/(app)/leads/new/page.tsx:241,243` — form field placeholders "Acme Freight" / "Head of Logistics". `src/app/(app)/admin/tenants/TenantsClient.tsx:151-152` — "Demo Logistics" / "demo-logistics" placeholders on tenant creation. These don't affect scoring or AI output, only what a user sees in an empty form field. Worth changing to industry-neutral examples ("Acme Corp" / "Head of Procurement") as a trivial part of R14, but not architecturally significant.

### What is **not** hardcoded (confirmed clean)
- **Conversation Intelligence** (`src/lib/ai/provider.ts:32`, `SYSTEM_PROMPT`) — reads "You are a trade show sales intelligence agent," genuinely industry-neutral already. Good news: this agent needs ICP *context added*, not bias *removed*.
- **Business Card OCR prompt** (`provider.ts:174`) — extraction-only, no industry framing.
- **ROI Agent** (`src/lib/agents/roi-agent.ts`) — pure math + a narrative summary with no industry-specific language.
- **Apollo enrichment** (`src/lib/enrichment/apollo.ts`) — a factual data source, correctly has no interpretive/ICP logic mixed in (matches the brief's §9 requirement directly — nothing to change here).
- **Dashboard** (`src/app/(app)/dashboard/page.tsx`) — no industry-specific copy or logic found.
- **Authority scoring** (`lead-scoring.ts`, seniority/title component) — uses a generic B2B title/seniority keyword list (CEO/CTO/COO/Director/VP/manager/senior), not logistics-specific, but also not tenant-configurable today. Not "biased" so much as "one-size-fits-all" — a tenant selling to, say, HR personas would want different title keywords (CHRO, HR Director) weighted as decision-makers, which this list doesn't recognize.
- **Products/solutions** — no such concept exists anywhere in the schema or code today. This isn't a hardcode to fix; it's new surface area (§3 of the brief) to build from scratch.
- **Event model** (`events` table: `id, tenantId, name, slug, location, startDate, endDate, status`) — no ICP-related column exists yet; a clean nullable FK addition, no conflicting logic to remove.

## C. Proposed Data Model

Per the brief's explicit instruction (§14: "Start simple... do not immediately create 15–20 ICP-related relational tables"), a single table with a validated JSON configuration blob, not a fully normalized schema:

```
icp_profiles
  id                  uuid PK
  tenantId            uuid → tenants (CASCADE)
  name                varchar(255)         -- e.g. "Freight Forwarders"
  description         text
  status              icp_status enum      -- draft | active | inactive
  version             integer default 1    -- bumped on every meaningful edit
  configurationJson   jsonb                -- Zod-validated, see below
  createdByUserId     uuid → users (SET NULL)
  createdAt / updatedAt
```
Indexes: `(tenantId)`, `(tenantId, status)`.

`events.icpProfileId → icp_profiles (SET NULL)`, nullable — `null` means "use the tenant's active default." This is additive-only; no existing `events` row is affected.

**`configurationJson` shape** (validated with Zod at the API boundary, not just trusted from the client — matches [14-coding-standards.md](14-coding-standards.md)'s existing validation conventions):

```ts
const ICPConfigSchema = z.object({
  companyFit: z.object({
    targetIndustries: z.array(z.string()),
    targetSubindustries: z.array(z.string()).default([]),
    targetCountries: z.array(z.string()).default([]),
    employeeSizeMin: z.number().nullable(),
    employeeSizeMax: z.number().nullable(),
    revenueRangeMin: z.number().nullable(),
    revenueRangeMax: z.number().nullable(),
    companyTypes: z.array(z.string()).default([]),
    relevantTechnologies: z.array(z.string()).default([]),
    excludedIndustries: z.array(z.string()).default([]),
    excludedCompanyTypes: z.array(z.string()).default([]),
    exclusions: z.array(z.string()).default([]),          // competitors etc.
  }),
  personaFit: z.object({
    targetDepartments: z.array(z.string()).default([]),
    targetJobFunctions: z.array(z.string()).default([]),
    targetTitles: z.array(z.string()).default([]),
    targetSeniority: z.array(z.string()).default([]),
    decisionMakerTitles: z.array(z.string()).default([]),
    economicBuyerTitles: z.array(z.string()).default([]),
    influencerTitles: z.array(z.string()).default([]),
    championTitles: z.array(z.string()).default([]),
    nonTargetPersonas: z.array(z.string()).default([]),
  }),
  problemFit: z.object({
    priorityPainPoints: z.array(z.string()).default([]),
    businessChallenges: z.array(z.string()).default([]),
    businessObjectives: z.array(z.string()).default([]),
    priorityUseCases: z.array(z.string()).default([]),
    triggerEvents: z.array(z.string()).default([]),
  }),
  buyingSignals: z.object({
    high: z.array(z.string()).default([]),
    medium: z.array(z.string()).default([]),
    negative: z.array(z.string()).default([]),
  }),
  products: z.array(z.object({
    name: z.string(),
    description: z.string().default(""),
    targetPersonas: z.array(z.string()).default([]),
    painPointsAddressed: z.array(z.string()).default([]),
    useCases: z.array(z.string()).default([]),
    keywords: z.array(z.string()).default([]),
    valueProposition: z.string().default(""),
    typicalDealValue: z.number().nullable().default(null),
  })).default([]),
  scoringWeights: z.object({
    companyFit: z.number(), personaFit: z.number(), problemFit: z.number(),
    buyingIntent: z.number(), engagement: z.number(), dataQuality: z.number(),
  }).refine(w => Object.values(w).reduce((a, b) => a + b, 0) === 100, "weights must sum to 100")
    .default({ companyFit: 25, personaFit: 20, problemFit: 20, buyingIntent: 15, engagement: 10, dataQuality: 10 }),
});
```

Note the default `scoringWeights` exactly matches the brief's §4 table and the *existing* `lead-scoring.ts` split (25/20/20/15/10/10, just relabeled Authority→Persona Fit and Need/Urgency→Problem Fit/Buying Intent to match the brief's terminology) — so a tenant with no customized weights gets numerically identical behavior to today.

Migration: `drizzle/0016_icp_profiles.sql`, hand-applied per the existing (unfixed, tracked separately as debt) migration process.

## D. Runtime Architecture — how ICP Context reaches each agent

```
Lead → tenantId, eventId
         │
         ▼
   ICP Resolver (src/lib/icp/icp-resolver.ts)
     getActiveICPForEvent(tenantId, eventId)
       → events.icpProfileId, if set
       → else tenant's status="active" icp_profiles row
       → else null (no ICP configured — see §E)
         │
         ▼
     ICPContext { profile, products, scoringWeights, version }
         │
    ┌────┼─────────────┬──────────────┐
    ▼    ▼              ▼              ▼
Conversation      Lead Scoring     Follow-Up      Company Intel Tab
Intelligence      (deterministic   Agent          (explainable fit —
(prompt input)    formula, inputs  (prompt input, replaces deriveICPFit())
                  from ICPContext) product context)
```

**One resolver function, injected wherever needed** — not five separate DB lookups, matching brief §7 exactly. Proposed interface:

```ts
// src/lib/icp/icp-resolver.ts
export async function getActiveICPForEvent(tenantId: string, eventId: string | null): Promise<ICPContext | null>
export async function getICPProfile(tenantId: string, profileId: string): Promise<ICPProfile | null>
export function validateICPConfiguration(config: unknown): ICPConfig   // throws on invalid, used by both the admin API and test mode
```

Each consuming agent takes `icpContext: ICPContext | null` as an added parameter (backward-compatible — `null` triggers today's behavior, see §E) rather than resolving ICP itself, so there is exactly one code path that decides "which ICP applies here."

## E. Backward Compatibility

**Mandatory, per brief §15.** Concretely:

- `getActiveICPForEvent()` returns `null` for any tenant/event with no `icp_profiles` row (the case for every existing tenant on day one of R14.2).
- Every consuming function's signature becomes `(..., icpContext: ICPContext | null)`, and every one of them **falls back to today's exact hardcoded values when `icpContext` is `null`**:
  - Lead Scoring: falls back to the current logistics-keyword bonus (A1) and current fixed 25/20/20/15/10/10 weights.
  - Follow-Up: falls back to the current logistics-flavored system prompt (A2) verbatim.
  - Company Intel Tab: falls back to the current `deriveICPFit()` logic (A3) until the tenant configures an ICP.
- This means **the hardcoded logistics behavior does not get deleted in R14** — it becomes the literal default fallback, preserved byte-for-byte where practical, just reachable through the same code path as a configured ICP instead of being the only path. This is a deliberate design choice to minimize regression risk, not an oversight — it can be revisited in a later release once every real tenant has an explicit ICP configured.
- No existing `leads`, `lead_scores`, `events`, or `followup_recommendations` row is touched by the R14.2 migration — it's purely additive (`CREATE TABLE`, one nullable `ALTER TABLE events ADD COLUMN`).

## F. Security — tenant isolation for ICP data

Follows the existing, already-audited pattern (see [08-multi-tenant-architecture.md](08-multi-tenant-architecture.md) — sampled routes found zero missing tenant filters):

- Every `icp_profiles` query filtered by `eq(icpProfiles.tenantId, session.user.tenantId)`, never client-supplied, identical to every other table in this codebase.
- `POST/PATCH /api/events/:id` (or wherever ICP assignment happens): explicitly validate `event.tenantId === icpProfile.tenantId` before allowing assignment — brief §16's exact requirement, a one-line guard.
- ICP Test Mode (§I below) must also be tenant-scoped and **must not** allow testing against another tenant's ICP profile.
- `platform_admin`'s existing cross-tenant exception (used for admin operations elsewhere) should **not** implicitly apply to ICP data unless a specific admin use case requires it — default to strict tenant-only access even for platform_admin here, and revisit only if a real need surfaces.

No new attack surface beyond "one more tenant-scoped table" — the isolation mechanism itself doesn't need to change, only be applied consistently to the new table.

## G. Versioning — keeping historical scores explainable

Per brief §12: don't silently reinterpret historical leads when an ICP changes.

- `icp_profiles.version` increments on every save that changes `configurationJson` (not on metadata-only edits like renaming).
- Add `icpProfileId` and `icpProfileVersion` (nullable) columns to `lead_scores` (and, for the same reason, `conversation_insights` and `followup_recommendations`) — recorded at the time each row is generated, never updated retroactively.
- A lead scored under ICP v1, where the tenant later edits weights into v2, keeps showing "scored against Freight Forwarders ICP v1" on that historical record — re-scoring (if ever triggered) creates a *new* `lead_scores` row against the current active version, exactly like today's existing re-scoring behavior (a new row per score generation, not an update).
- This is additive to existing tables (nullable columns), so it doesn't conflict with §E's backward-compatibility requirement — old rows simply have `icpProfileId: null`, correctly meaning "scored under the pre-ICP hardcoded default."

## I. Risks

| Risk | Severity | Mitigation |
|---|---|---|
| **Regression in existing (logistics-default) scoring/follow-up behavior** for tenants that never configure an ICP | Medium | §E's fallback design — `null` context reproduces today's exact behavior; test this explicitly before/after (R14.2's own test plan) |
| **Migration drift** — this repo has no migration runner (tracked separately in [TECHNICAL-DEBT.md](TECHNICAL-DEBT.md) H2); a new table is one more manual `psql` step across environments that can be missed | Medium | Not fixed by R14 — apply the same manual discipline as every other migration, explicitly call it out in the R14.2 deploy checklist |
| **`CompanyIntelTab.tsx`'s duplicate fit logic (A3) silently diverges further** if only `lead-scoring.ts` gets ICP-aware and the UI tab is left on the old hardcoded path | Medium-High if missed, Low if addressed | Explicitly included in the Impact Map (§B) and Implementation Plan (§H) — do not treat this as a "nice to have," it's the brief's "one source of truth" principle being actively violated today |
| **Prompt-injection-style risk from tenant-supplied ICP text reaching Gemini prompts unsanitized** (target industries, pain-point keywords, etc. are free text, inserted into follow-up/conversation prompts) | Low-Medium | Existing prompts already defend against the model inventing facts / taking action; the same "forbid X" prompt rules apply. Not a new class of risk beyond what already exists with lead-supplied notes reaching these same prompts today — but worth an explicit regression check in R14.4/R14.6 |
| **Scope creep toward a generic rules engine** (explicitly warned against in the brief) | Medium | The proposed data model (§C) is one JSON-configured table, not N relational tables; resist requests to generalize further during implementation |
| **Weights-sum-to-100 validation gap** if enforced only client-side | Low | §C's Zod schema validates server-side at the API boundary, matching existing API conventions |

No risk identified that should block proceeding — all are manageable with the mitigations above, which is reflected in the recommendation below.

## J. Recommendation

Conditions:
1. **R14.2 must include fixing the A3 duplicate-fit-logic finding**, not just the scoring engine and prompts — otherwise R14 ships with two disagreeing "ICP fit" displays in the product, which is worse than the current single (if hardcoded) one.

3. **No code changes happen until this document is explicitly approved** — this session stops here, per STOP #1.

This assessment found the situation slightly more involved than the prior session's plan (three hardcoded-logic locations instead of one, including a genuine architectural duplication in the UI layer), but nothing here changes the brief's core premise: **one agent, configuration-driven, no forks required.** The existing scoring formula, orchestrator, and agent structure are all sound and reusable as-is — R14 is additive, not a rewrite.
